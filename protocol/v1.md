# Protocol version 1

## State root and transport

The CLI injects `GDBG_STATE` into the Godot process. Both sides use:

```text
<GDBG_STATE>/debug/ipc/command
<GDBG_STATE>/debug/ipc/result
<GDBG_STATE>/debug/ipc/temp_script.gd
```

The CLI writes one `command` file and waits for one `result` file. The runtime
consumes the command; the CLI consumes the result. Commands are serialized, so
version 1 does not define concurrent request identifiers.

## JSON command

```json
{
  "protocol": 1,
  "cmd": "input",
  "args": {
    "op": "tap",
    "action": "interact"
  }
}
```

`cmd` is required. `args` is an array for project console commands and an
object for bridge-owned commands. An optional `screenshot` object asks the
runtime to schedule a screenshot after a console command.

Bridge-owned commands in version 1 are:

- `screenshot`: capture one or more viewport images.
- `fetch`: retrieve an asynchronous capture by `capture_id`.
- `input`: list, press, release, tap, or hold Godot input actions.
- `perf` samples per-process-frame wall time and Performance monitors.

For `perf`, send `args.op` as `start`, `status`, or `stop`. `start` accepts an
optional custom monitor name `prefix` and a default JSON output path `out`.
`status` returns `active`, `frames`, and `elapsed_sec`. `stop` returns the
summary in `result` and accepts an `out` override. CLI output paths resolve
relative to the invoking directory. Starting an active sampler or stopping an
inactive sampler returns an error.

`frame_ms` measures consecutive sampler callbacks. `pre_ms`, `draw_ms`, and
`post_ms` split that interval at the two rendering signals. Intervals lacking
rendering signals contribute only to `frame_ms`. An empty series is `{}`.
`valid_draw_pct` counts intervals where the cumulative draw counter advanced by
exactly one. `valid_draw_fps` divides that count by elapsed wall-clock seconds.
`over_16_0ms_pct`, `over_16_7ms_pct`, and `over_33_3ms_pct` use all
sampled intervals. Timing, built-in metrics, and numeric `custom_monitors`
include the arithmetic mean, nearest-rank p50/p95/p99, and maximum. Memory
metrics use MiB. `gdbg perf diff` reports after minus before for each field.

Screenshot capture requires a rendered viewport. A runtime using Godot's
headless display returns an error result. Clients should relaunch the game in
windowed mode before requesting screenshots. Deterministic video recording uses
`gdbg record` (Godot Movie Maker plus JSONL timeline events) outside the live
file IPC channel.

All other commands are joined as console text and delegated to the project's
`DebugBridgeHost`. This is the extension boundary used by game-defined console
modules.

### Remote profiler

`gdbg run game` and `gdbg test scene` accept `--remote-profile <file.json>`.
Godot 4.7.1 uses a little-endian uint32 byte length followed by one binary
Variant Array `[message, thread_id, payload]`. The collector enables
`profiler:servers` with `[true, [128, false]]` and `profiler:visual` with
`[true]` on main thread 1. Godot sends `[signature, id]` in
`servers:function_signature`. It carries script data inside `servers:profile_frame`.
The frame starts with its number and five times in seconds, then a server count.
Each server supplies its name, slot count, and function/seconds pairs. A final
slot count precedes script tuples `[id, calls, self, total, internal]`.
`visual:profile_frame` carries a frame number, slot count, and triples of area
name, CPU timestamp, and GPU timestamp in milliseconds. Headless sessions can
have zero visual frames.

The `phases` object defaults to `default`. A project can bracket work with
`EngineDebugger.send_message("gdbg:phase_start", [name])` and a matching
`gdbg:phase_end`. Nested markers attribute frames to the innermost phase.
`server_frames` counts complete server packets and `script_frames` counts those
containing script functions. Script and server means include every server frame
in the phase. `servers` maps server and function names to mean milliseconds.
`visual` reports mean CPU and GPU durations between consecutive area timestamps,
including zero contribution for frames where an area was absent.

## JSON result

Successful result:

```json
{"protocol":1,"result":"pong"}
```

Error result:

```json
{"protocol":1,"result":null,"status":"error","message":"Unknown input action: jump"}
```

Asynchronous captures may return `capture_id`, `status: "pending"`, and a
human-readable `progress` value before becoming ready.

## Plain text compatibility

A command file that does not begin with `{` is treated as console text. A
non-JSON result is returned verbatim. This compatibility path is unversioned;
new integrations should use JSON envelopes.

## Script staging

`gdbg debug script file.gd` writes the script to `temp_script.gd`, then sends
the project console command `script`. The host project decides whether and how
to execute staged scripts; GDBG does not grant additional sandboxing.
